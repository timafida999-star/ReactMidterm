# Codex Exilis — подготовка к защите

## Что делает приложение

Codex Exilis — каталог вымышленных фракций, персонажей, оружия, кораблей и планет. В исходном JSON находятся 120 записей. Симулированный API возвращает Promise после задержки, читает localStorage, выполняет поиск и фильтрацию, затем сортирует и разбивает результат на страницы.

## Дерево компонентов

```text
App
├── Header
├── main: каталог
│   ├── Hero
│   └── FilterBar + ItemList
│       ├── ItemCard × N
│       │   ├── EntityImage
│       │   └── Badge
│       └── Pagination
├── ItemDetail ИЛИ Protocol
├── Footer
├── AddItemForm (условно)
└── уведомление (условно)
```

На загрузке вместо ItemList отображается SkeletonGrid; при ошибке или отсутствии результатов — AsyncState.

## Где хранится state

| State                                | Владелец         | Причина                                                    |
| ------------------------------------ | ---------------- | ---------------------------------------------------------- |
| Поиск, фильтры, сортировка, страница | App              | Эти значения нужны Header, FilterBar и Pagination          |
| Данные, статус запроса, ошибка       | useAsyncResource | Одинаковая логика жизненного цикла для списка и досье      |
| Черновик, ошибки полей, отправка     | AddItemForm      | Остальные компоненты не должны знать о незавершённой форме |
| Ошибка загрузки картинки             | EntityImage      | Локальная деталь конкретной карточки                       |
| Маршрут                              | useRoute         | Синхронизация с URL и кнопками назад/вперёд                |
| Избранное и уведомление              | App              | Доступны на разных экранах                                 |

## Поток данных

`input.onChange → changeQuery → setQuery → новый render → loader → useEffect → codexApi.list → Promise → setState → render списка`.

Данные передаются вниз через props. Дочерний компонент сообщает о действии наверх через callback. Например, Pagination вызывает `onPage`, а App обновляет query. ItemCard сам не меняет массив данных и не читает localStorage.

## Контролируемая форма

У каждого поля есть `value={values[name]}` и `onChange={change}`. Источник истины — React state. Обновление `{ ...previous, [name]: value }` создаёт новый объект. Валидация находится в общей функции `validateRecord`; её также вызывает API. Ошибка сохранения не очищает черновик. Повторная отправка во время активного запроса заблокирована.

## Render, commit и повторный render

Render вычисляет JSX из props и state. Commit применяет необходимые изменения к DOM. Изменение state запускает новый render владельца и обычно его потомков; это не означает полной перерисовки DOM. React сравнивает элементы и вносит только нужные изменения. React монтирует приложение в DOM один раз через createRoot; прикладной код не добавляет и не удаляет DOM-узлы вручную.

## Снимки state и batching

Обработчик видит значения state из того render, в котором он был создан. `setState` планирует следующий render и не меняет локальную переменную мгновенно. React группирует обновления; поэтому `setRevision(value => value + 1)` корректно использует предыдущее значение, а `changeQuery` одновременно меняет фильтр и сбрасывает страницу.

## Identity и keys

React различает элементы по типу, позиции и key. Карточки используют `item.id`, поэтому сортировка не переносит локальное состояние изображения на другую запись. Индекс массива здесь был бы неверным ключом. В skeleton индекс допустим: это статический набор однотипных декоративных заглушек.

`ItemDetail key={route.id}` создаёт новый экземпляр при переходе к другому досье. AddItemForm существует только при открытом модальном окне: закрытие размонтирует форму, открытие начинает новый черновик. Компоненты определены на уровне модулей, а не внутри App.

## useEffect и зависимости

`useAsyncResource` зависит от `loader` и `revision`. loader мемоизирован через useCallback и меняется при изменении параметров запроса. `useDebouncedValue` зависит от текста и задержки. `useRoute` один раз подписывается на hashchange; cleanup удаляет подписку. Ещё один effect слушает storage для синхронизации открытых вкладок.

Effect нужен для синхронизации с внешней системой: API, таймером, URL, событием браузера. Фильтрация и сортировка — чистые вычисления внутри API, отдельный effect для них не нужен.

В StrictMode React в разработке проверяет эффекты последовательностью setup → cleanup → setup. Правильная отмена предотвращает лишние завершения запросов. Это не повод отключать StrictMode.

## Cleanup, stale closures и race conditions

Каждый запрос получает собственный AbortController. Cleanup вызывает abort: таймер запроса очищается, Promise отклоняется с AbortError. Обработчик завершения дополнительно проверяет `signal.aborted`. Даже если старый источник проигнорирует отмену, старые данные не попадут в state.

Пример гонки: запрос «Ash» стартовал раньше запроса «Vesper», но завершился позже. Без проверки он мог бы заменить актуальный список. Тест `async-resource.test.jsx` специально завершает старый Promise последним.

Stale closure — функция сохранила устаревшие значения из предыдущего render. Решение здесь: полные зависимости эффектов и callbacks, функциональные обновления счётчиков, отдельный сигнал отмены для каждого запроса. Подавление предупреждений о зависимостях не используется.

## Четыре состояния

1. Loading: skeleton на запросе списка, индикатор при загрузке досье и отправке формы.
2. Error: сообщение о конкретной проблеме и повторный запрос. Испорченные данные не заменяются автоматически.
3. Empty: нулевой результат с возможностью сбросить фильтры; отдельный текст для пустого избранного.
4. Success: список, пагинация, досье; после добавления — уведомление и новое досье.

## Возможные изменения на защите

**Добавить фильтр по происхождению:** добавить `origin: 'All'` в DEFAULT_QUERY, контролируемый select в FilterBar, условие в selectRecords, параметр в requestQuery и его зависимости. Обработчик должен сбрасывать страницу.

**Добавить поле в карточку:** прочитать его из item в ItemCard; данные уже пришли через props. Если поле новое, обновить JSON, форму, валидацию и проверку схемы в API.

**Изменить сортировку:** добавить значение в SORT_OPTIONS и comparator в selectRecords. Сортировать до slice, учитывать стабильный ID при равных значениях.

**Добавить reset:** использовать DEFAULT_QUERY в обработчике, а не менять input через DOM. В текущей реализации Reset сохраняет выбранный размер страницы.

**Продемонстрировать ошибку:** в отдельном тестовом профиле сохранить текущий JSON, временно испортить значение `codex-exilis:archive:v1` через DevTools, перезагрузить, показать Error, восстановить сохранённый JSON и нажать Retry connection. Не делайте это поверх важных пользовательских данных.

**Что произойдёт без cleanup:** старые запросы и таймеры продолжат работу; устаревшее завершение может заменить актуальный state. Слушатели событий могут накапливаться при повторном монтировании.

## Что ещё требуется перед сдачей

Исходники и production build готовы как файлы. Для выполнения критерия Deployment необходимо разместить приложение на публичном статическом хостинге, проверить ссылку в чистом браузере и отправить настоящий GitHub URL. Локальная ссылка и ZIP сами по себе не заменяют обязательное развёртывание.
